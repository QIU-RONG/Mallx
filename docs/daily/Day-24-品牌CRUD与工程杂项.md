## 二、L5②：三处设计决定（都有对照物）

### ① DTO **带** `status`，而 `CategoryCreateDTO` **不带** —— 判据是「有没有消费方」

| 表 | `status` 的消费方 | DTO 给不给 |
|---|---|---|
| `categories` | **没有**（C 端 `tree()` 不过滤 status；上下架由商品自己管） | 不给 |
| `brands` | **有**：C 端 `listEnabled()` 过滤 `status=1`、管理端 `listAll()` 含停用 | **给** |

★ 判据是「**有没有真实消费方读这个字段**」，不是「表里有没有这一列」。
品牌必须能在**创建时**就停用，否则只能「先建启用的、再调一次 update 停用」—— 白白多一次写入。
⚠️ 两处做法不一致的地方**必须写下理由**，否则后来者会以为其中一个漏了。

### ② `countByBrandId` **没有**和 `countByCategoryId` 合成一条带 `<if>` 的 SQL

两条 SQL 结构完全相同（只差 `brand_id` / `category_id` 一列）。**为什么不合成**：
「按哪个列数」由**业务语义**决定（删分类 vs 删品牌），不是由数据决定。
合成一条的结果是：调用方写错列名，**编译期、运行期都不报错**，
只是「拿分类的计数去判品牌能不能删」—— 一个永远为 0 的检查。
（同族：Day 19 的 `categoryId` 两入口口径漂移。）

### ③ 局部更新：`null` = 不动，`""`（空串）= 清空

| 字段 | `null`（不传） | `""`（空串） |
|---|---|---|
| `name` | 不动 | **400**（Service 显式挡 —— `@Size` 管不了空串） |
| `logo` / `description` | 不动 | **清空**（这是本端点唯一的清空手段） |
| `status` | 不动（★ **不是**「停用」） | 不适用（`@Min/@Max` 只收 0/1） |

★ `BrandUpdateDTO` **不能**复用 `BrandCreateDTO`：同一个 `null`，创建时含义是「走默认值 1（启用）」、
更新时含义是「不动」，**两处相反**。

## 三、L5②：验收的核心三对（单侧断言证明不了任何事）

### 对①：权限矩阵的正反两面

| 身份 | `POST /api/admin/brands` | 含义 |
|---|---|---|
| 匿名 | **401** | 未登录 |
| `demo`（C 端 token） | **403** | C 端 token 无 `perms` |
| **`op_order`**（ORDER_ADMIN） | **403** ★ | **反向对照** —— 只有 `order:*` |
| **`op_product`**（PRODUCT_ADMIN） | **200** ★ | 有 `brand:*` |

★ 只用全权 `admin` 测 = 什么都证明不了。`op_order` 连 `GET`（`brand:list`）都 403 —— 这一条才说明
「权限是按岗位分的」，而不是「登录了就能用」。

### 对②：`status` 的两端口径（★ 本日最值钱的一对）

同一个品牌、同一时刻、`status=0`：

| 端点 | 结果 | 断言编号 |
|---|---|---|
| C 端 `GET /api/brands` | **看不见它** | #23 |
| 管理端 `GET /api/admin/brands` | **看得见它** | #24 |

**同一轮里两条都断，才证明「status 真的生效」**：
- 只断「C 端看不见」⇒ 可能是接口坏了 / 缓存了；
- 只断「管理端看得见」⇒ 可能是它压根不过滤 `status`（那就等于这个字段没生效）。

★ 再加一条 #26（改回 `status=1` 后 C 端**又能看见**）—— 这一条排除「C 端其实永远看不见」的
第三种解释。**三条合起来才闭环。**

### 对③：删除引用校验的「软删陷阱」

`@TableLogic` 会让 `productMapper.selectCount` 自动追加 `is_deleted = 0`
⇒ 漏算已软删商品 ⇒ 校验放行 ⇒ 物理删品牌撞 `fk_product_brand`（NO ACTION）→ **现场 500**。

本脚本把这条钉成 4 步断言（#31 → #34）：

```
建商品挂到品牌上  →  删品牌 = 400（有引用）
   ↓
软删该商品（is_deleted=1，外键仍在）
   ↓
删品牌 = 400  ★★★ 这一条才是判据
```

★ 与 Day 18 的 `countByCategoryId` 是**同一个缺陷的两个出口** —— 同一条判据第 2 次落地：
**引用计数的口径必须与外键的口径一致（外键不认识 `is_deleted`）。**

## 六、T4：Swagger 补 Authorize 按钮

**问题**：V1.0 没有前端，**界面就是 Swagger UI**；而它**没有 Authorize 按钮**
⇒ 「Try it out」面板没有地方填自定义 header ⇒ **所有受保护接口在这个唯一的界面上都调不通**
（此前只能手工用 curl 拼 header）。

**修法**（`OpenApiConfig`）—— ★★ 必须**两半都写**，这是最容易漏的一半：

| # | 代码 | 作用 |
|---|---|---|
| ① | `components.addSecuritySchemes("bearerAuth", ...)` | 告诉 UI「有这么一个认证方式、它叫什么名字」 |
| ② | `addSecurityItem(new SecurityRequirement().addList("bearerAuth"))` | 告诉 UI「每个操作默认可选带上它」 |

⚠️ 只写 ① 的现象：UI 上**会画出按钮**，但操作上**不会带上它** ——
「按钮存在 ≠ 请求带上 token」，是两件事，且**不报错**。
⚠️ scheme 名字（`bearerAuth`）在 ① 与 ② 之间**必须逐字一致**，
对不上时 UI 不报错、只是**静默不生效**（同「XML 方法名＝`id` 逐字符」那条铁律）。

⚠️ 这里声明的只是**文档元数据**，不参与任何鉴权决策 —— 防线始终是 `SecurityConfig` 的过滤器链
+ `@PreAuthorize`。**在 Swagger 上填了 token 不代表能调通，填错/过期一样 401。**

**实证（本日实测）**：

| 检查 | 结果 |
|---|---|
| `GET /v3/api-docs` 含 `securitySchemes` | ✅ 1 处 |
| 其中 `bearerAuth` 出现次数 | ✅ **3**（scheme 名 + `name` 字段 + security requirement） |
| 顶层 `security:[{"bearerAuth":[]}]` | ✅ 在（⇒ 会挂到每个操作上，正是 §六 表格里 ② 那一半） |
| `GET /swagger-ui.html` | **302**（springdoc 正常重定向到 `/swagger-ui/index.html`） |
| 跟随重定向 | **200**，页面含 `swagger-ui-bundle`（渲染入口在） |

★ 说明：这是**接口层**证据 —— Swagger UI 的 Authorize 按钮就是照这份 JSON 渲染的。
本项目验收一律走 HTTP，**不引入「打开浏览器看一眼」这种手工步骤**
（那样它就不会出现在任何回归里）。

   而文档能这么写，是因为**代码已经这么做了**。
