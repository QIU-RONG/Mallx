## 1. 权限矩阵：页面 × 权限码

菜单显隐与按钮显隐都按这张表。⚠️ 全部只是**体验** —— 真正的边界是后端每个端点上的
`@PreAuthorize`；直接敲 URL 会被挡成 403，而**管理端 403 是常态**（见 `api/http.ts`）。

| 页面 | 进入条件（列表码） | 写操作码 |
|---|---|---|
| 分类管理 | `category:list` | `category:create` / `category:update` / `category:delete` |
| 品牌管理 | `brand:list` | `brand:create` / `brand:update` / `brand:delete` |

## 2. 每个页面「不能想当然」的地方

### 分类（`CategoryList.vue`）

- **树不是平表**：`GET /admin/categories/tree` 返回 `children` 嵌套 ⇒
  表格必须 `row-key="id"` + `:tree-props="{ children: 'children' }"`，
  否则子分类会整块不显示（且不报错）。下拉需要扁平行 ⇒ 走 `utils/tree.ts#flattenCategories`。
- **只允许两级**：新增子分类时父分类必须是顶级 ⇒ 页面只拿顶级分类当父选项，
  子分类行不出现「加子分类」按钮。这是「在界面上表达规则」，不是规则本身。
- **改不了层级**：`CategoryUpdateDTO` 约定 `parentId=null` 一律「不动」（想改层级只能删重建）。
  所以编辑对话框**不提供父分类选择** —— 提供了才是骗人。
- **删除是物理删 + 三重校验**：有子分类 / 有商品引用（★ 含软删商品）都 400。
  所以「删除失败」是正常业务结果，文案由拦截器给，页面不吞。

### 品牌（`BrandList.vue`）

- **管理端含停用**：C 端 `GET /api/brands` 只给 `status=1`，本页走 `/admin/brands` 全都要 ——
  「要重新启用一个品牌，必须先看得见它」。
- **`name` 有 UNIQUE**：重名由后端翻成 400（不是 500）。界面提前写一句「重名会保存失败」。
- **停用 ≠ 删除**：停用只影响 C 端筛选；删除是物理删且要过商品引用。文案按这个区别写。

### 优惠券（`CouponList.vue`）

★★ **两个面额字段互斥** —— 本页最容易犯的错，也是唯一为它单独抽纯函数的原因：

```text
FIXED    → 必须带 discountAmount，且【不许】带 discountRate
DISCOUNT → 必须带 discountRate，且【不许】带 discountAmount
```

后端对「两个都带」直接 400（`CouponServiceImpl` 的关系校验）。而界面上**切换券类型不会
自动清空另一侧输入**：用户先按「满减」填 20，再切「折扣」—— 20 会跟着发出去，
报错却叫「折扣券不能同时填写 discountAmount」，用户会说「我明明没填」。

⇒ `utils/coupon.ts#buildCouponPayload` **按类型只挑该有的那个字段**，残留值一律不下发。
这条被单测直接钉住（连「表单里残留 0.8」这种场景都写了用例）。

其余三条：

- **只有 列表 / 新建 / 删除**：没有「改券」是决策 —— 券发出去后改面额会和已领用户的预期冲突，
  真实做法是「作废旧券 + 新建一张」。界面因此没有编辑入口。
- **分页参数叫 `page`** 而不是 `current`（券 Controller 与其它模块不是同一套），照签名写。
- **被领过的券删不掉**（`user_coupons` 引用，后端 400）。

### 用户（`UserList.vue`）

- **`user:status` 只发给超管**：订单管理员能看列表与详情，但看不到禁用按钮 ——
  这是「每个端点一个码」的既定分发，不是前端漏写。
- **定点端点**：`PUT /{id}/status` 只改状态，不会顺手覆盖昵称（这就是它不并进 `PUT /{id}` 的理由）。
- **禁用不等于立刻踢下线**：token 未过期前接口仍可用，只是下次登录被拒。
  这句写进确认框 —— 不写，运营会以为「点了就该立刻踢下线」。

### 角色权限（`RoleList.vue`）

- **`code` 不可改**：它已经以 `ROLE_xxx` 的形式签进了所有存量 token；`RoleUpdateDTO` 里根本没有这个字段。
  编辑框里把 code 显示成只读标签，并写明理由。
- **两条超管护栏**：不许删 / 停用 `SUPER_ADMIN`（否则谁也进不来）；不许**减少**它的权限（只许增）。
  界面把「已授予的项」禁用，只能勾新的 —— 这才是护栏②的界面表达。
  ⚠️ 判据用的是**打开对话框时**的后端集合，本轮新勾的项不在其中 ⇒ 保存前勾了又取消不会自锁。
- **分配是「全量替换」**：传的是「改完之后要有的全集」，不是增量。
  `null` 会 400（防止漏传静默清空），空数组 `[]` 才是「清空」。
- **权限字典只读**：权限码是代码资产，每个码必须有一个 `@PreAuthorize` 引用它 ——
  界面没有「新建权限」，这不是没做完。

## 3. 菜单为什么从模板里抽出来

原来是 4 个写死的 `<el-menu-item>` + 1 个 `v-if`。加到 9 项之后，两个问题同时出现：

1. **入口与权限码的对应关系不可测** —— 模板里的 `v-if` 链只能靠肉眼；
2. **「路由加了、菜单忘了」** 这类漏项没有任何护栏。

⇒ 改成 `utils/menu.ts`：`ADMIN_MENUS` 纯数组 + `visibleMenus(perms)` 纯函数。
后者的单测直接钉住三件事：

- 全码 → 9 项全在；
- **空 perms（C 端 token / 畸形 token）→ 只剩 3 个底座入口**；
- 只给 `coupon:list` → 券入口在、用户/角色入口不在。

★ 「概览 / 商品 / 订单」刻意**不挂码**：它们是所有管理角色的底座，
挂上码只会让新角色配错一个码就整块消失（而这三页的接口本来就要求登录）。

## 4. 顺手修掉的事故：「取消」= 继续执行

改造前，项目里 4 处二次确认都长这样：

```ts
await ElMessageBox.confirm('确定删除？', ...).catch(() => null)
await api.delete(id)          // ← 用户点了「取消」，这行照样执行
```

`confirm` 在**取消时 reject**，`.catch(() => null)` 把 reject 吞掉之后函数继续往下走。
最危险的一处是售后的「执行退款」：点「再想想」，钱照样退出去 —— 不报错、不告警，
只会在某天对账时发现「怎么多退了一笔」。

**修法**：`utils/confirm.ts#confirmAction` 把两种结果收敛成布尔值，调用方写 `if (!ok) return`；
并回改 **6 处**旧调用（商品删除 / 订单发货 / 订单取消 / 售后确认收货 / 售后执行退款 / 退出登录）。

单测锁的是**因果关系**而不是弹窗长相：取消 → `false`、且**不抛异常**（抛了调用方还得多包一层 try）。

★★ **控制组抓到了它自己的假绿** —— 第 ④ 组第一次跑时<b>没有红</b>。原因是我把用例写成了：

```ts
await expect(async () => {
  const ok = await confirmAction('要删吗？')
  expect(ok).toBe(false)
}).not.toThrow()
```

`toThrow` 不会 await 返回的 Promise ⇒ 回调里的断言失败也照样 PASS。改法：

```ts
await expect(confirmAction('要删吗？')).resolves.toBe(false)   // 不抛 + 值为 false，一条断言覆盖两件事
```

⇒ 这就是本项目反复说的那句话：**控制组的价值不是「证明我写对了」，而是「证明我的测试会红」**。
如果没有第 ④ 组，这条假绿会一直躺在「47/47 全绿」里。

★ Day 53 的控制组脚本里 `EXPECTED_TOTAL` 是硬编码的 21 —— 本日测试总数变了，它已同步改为 47，
并**重跑确认 7/7 仍全部命中**（`_d53-ctrl-rerun.txt`）。这与 D43-B 是同一类问题：
**护栏自己也会漂移，而且漂移时先制造假红**。改测试条数时必须一起改它。

   本轮只有类型 / 静态 / 单测三层验证。下次起全栈时按 §2 的每条「不能想当然」过一遍。

   要做得先加接口（那是另一天的活，不是「补页面」）。
4. **分类层级不可改**、**券不可编辑**：都是后端既定语义，不是界面缺口（见 §2）。
