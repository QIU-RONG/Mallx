# Day 71 · 售后类型改为可选（已发货可二选一）

用户需求：**「售后类型应该是可以选择的」** → 选择方案 1：未发货仅退款；已发货两种都行。

## 规则变化

| 订单状态 | 之前 | 现在 |
|---|---|---|
| PAID（未发货） | 仅退款 | 仅退款（不变） |
| SHIPPED（已发货） | 只能退货退款 | **仅退款 / 退货退款 二选一** |
| COMPLETED（已完成） | 只能退货退款 | 只能退货退款（已签收，不寄回等于白送） |

- 后端：RefundType.isOrderStatusAllowed 放宽；pply 改为按「状态是否允许该类型」判断，
  400 文案改为「可选：[...]（未发货只能仅退款；已发货可仅退款或退货退款）」；
- 前端：申请售后弹窗的只读输入框改成 el-select，只列出当前状态允许的类型，
  默认选「退货退款」（签收后要退，通常需要寄回）；
- **库存口径（关键）**：已发货订单的「仅退款」= 没收到货/拒收 ⇒ 执行退款时**不回补库存**，
  否则在途的那件会被算成可售，直接超卖；未发货的仅退款仍照常回补。
  判定用 orders.shipped_at（不是 status —— 执行退款时订单已经是 REFUNDED）。

## 验证

- 单测 RefundServiceImplTest **13 / 13**：新增「已发货仅退款允许」「已完成仅退款 400」
  「已发货仅退款不回补库存」「未发货仅退款照常回补」；
- 主链路 e2e **40 / 40**；
- 实测：SHIPPED 订单申请仅退款 → 审核 → 执行退款，库存 vailable/sold 前后一致（117/3），订单转 REFUNDED；
- 前端实测下拉两项：仅退款 / 退货退款。

## 没做的 / 需要注意

1. 已发货仅退款后，如果货最终仍送达并被签收，**需要人工调库存**（系统没有「在途回补」这一环）；
2. day46 的 Docker 版全链路脚本里，B2 断言已从「已发货选仅退款 400」改为
   「允许 + 撤销」，但本机无 Docker，只跑了单测与手工接口验证；
3. 已完成订单仍然只能退货退款 —— 如果要做「仅退款（不退货）」，那是另一个业务决策（白送风险）。
