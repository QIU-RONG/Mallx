## 一、D46-A：权限总数【单一来源】护栏

### 事故回放

Day 46 新增 5 条退款权限（id 42–46），权限总数 41 → 46。
但这份事实被**硬编码钉在 5 个地方**，改的时候只想起来一处：

| # | 位置 | 漏改后果 |
|---|---|---|
| 1 | `.github/workflows/ci.yml` | initdb 数据判据等不到 46 ⇒ **整条 pipeline 红** |
| 2 | `day24-perm-apply.py` | `EXPECT_PERM_MAX_ID` / `EXPECT_PERM_TOTAL` |
| 3 | `day25-sql-strict-check.py` | `EXPECT_PERM_TOTAL`（还有 `EXPECTED_FILES` 16→18） |
| 4 | `day25-compose-verify.py` | B2 断言 `n_perm == 46` |
| 5 | `day43-run-full-stack.ps1` | **不进 CI** ⇒ 漏了只会在本机静默等满 90 秒，没人报红 |

红的位置（CI 第 7 步）离真因（SQL 里多了 5 行）有十万八千里。

### 修法：不把 5 处再改一遍，而是让这份事实只有一个来源

`backend/loadtest/day47-perm-count-guard.py` —— 真值从 `backend/sql/*.sql` 的
`INSERT INTO permissions` **静态推导**，再逐处核对；**脚本自身不硬编码 46**。

| 段 | 验什么 |
|---|---|
| A | 三条与具体数字无关的**不变式**：id 不重复、1..max 连续、每个补发文件都配了 `setval` 序列校准 |
| B | 逐处核对 9 个声明点。★「一处都没命中」判 FAIL —— 正则悄悄失配造成假绿，比红更坏 |
| C | ① 判据不许写成 `>=`；② **漏网检测**（第 6 处硬编码会自动现形）；③ SQL 文件数 vs `EXPECTED_FILES` |

### 控制组（4 组，本地 `python backend/loadtest/_d46a_ctrl.py`）

| 变异 | 结果 |
|---|---|
| ① `day25-compose` 的 46 退回 41 | 红 **1** 条（精确点名 B7） |
| ② 新建脚本写 `EXPECT_PERM_TOTAL = 99` | 红 **1** 条（C2 抓到未登记声明点） |
| ③ SQL 加一条权限而常量不动 | 红 **9** 条（★ 本脚本唯一存在的理由） |
| ④ 判据写成 `>= 46` | 红 **2** 条 |

零误伤 —— ①②只红了预期那一条。

### 两条自己踩出来的坑

1. **护栏第一版在 CI 上红了，本地却是绿的**：我在 ci.yml 新加的注释里写了
   `Wait for initdb（permissions=41）`（描述旧事故），被 B2 段当成一处声明点抓出来。
   ⇒ 教训一：**注释里的旧数字也是对后来者的误导**，措辞改成「还写着旧值」；
   ⇒ 教训二：**改完任何文件都要重跑护栏**（我是提交后才发现的）。
2. **探针文件叫 `_perm-drift-probe.py` 时控制组 0 失败**：护栏扫描豁免了 `_*.py`
   （本项目内部工具约定）⇒ 控制组被自己的豁免规则绕过。改名成 `day99-drift-probe.py` 才测出真东西。
   ★ 这正是「控制组」存在的意义：**它会告诉你护栏在哪儿是瞎的。**

## 二、#88：退款 / 售后的前端落地

后端 10 个售后端点 Day 46 就已就位，前端一直是空的。

### admin-app（运营审核台）`views/RefundList.vue`

- **按钮显隐 = 状态机 × 权限码，两把锁**：
  状态机让人看不见当前做不了的动作；权限码让没码的人根本没按钮。
  两边都只是体验 —— 真边界是后端 SQL 的 `WHERE status = '...'` 与 `@PreAuthorize`。
- 打款按钮的二次确认写清后果并声明**不可撤销**（它是全项目唯一动钱的端点）。
- 详情用时间轴画五个时间点，★ **只收非空时间戳**（没走到那一步就是 null，
  判空而不是假定有序，否则会出现「已完成」排在「已申请」前面）。
- 菜单入口按 `refund:list` 显隐。

### mall-app（买家侧）`views/MyRefunds.vue` + `OrderDetail.vue`

- 我的售后：进度、撤销、退货填物流单号；★ **拒绝原因必须显眼**
  （买家不知道为什么被拒，就会反复申请）。
- 「申请售后」：★ **类型由订单状态锁定为只读选项**
  （未发货→仅退款、已发货→退货退款）。这是**跨对象的关系校验**，`@Valid` 表达不了，
  前端锁选项是体验，真正的守门在 `RefundServiceImpl#apply`（选错会 400，且报错会指明该选哪个）。
  界面上还写明：退款额由系统按实付算，**不支持自填**。

### 一个容易写错的细节

两个前端的 `http.ts` 已经统一处理了「HTTP 200 + body.code!=0」与 403 的提示，
所以页面里只吞 rejection、不再弹一次 —— **一个错误弹两遍比不弹更糟**。

### 验收：`day47-refund-fe-e2e.py`（27 条，进 CI）

与 day46 的分工：day46 直连 8080 验「后端对不对」；本脚本走 5173/5174 代理，
额外验「**前端类型定义里声明的字段名对不对**」——
字段名写错在前端只会**静默显示空白**，不报错，直连后端永远验不出来。

## 三、V1.4 后半段：远端托管物料

### 交付物

| 文件 | 作用 |
|---|---|
| `deploy/docker-compose.prod.yml` | 生产编排：caddy + app + postgres + redis + rabbitmq，镜像来自 registry |
| `deploy/Caddyfile` | 自动 HTTPS + **显式拒绝 `/actuator/**` 与 swagger** |
| `deploy/.env.prod.example` | 生产环境变量样例（必填项用 `:?`，缺失即拒绝启动） |
| `deploy/deploy.sh` | 一键部署：**健康检查 + 失败自动回滚** |
| `deploy/backup-db.sh` | `pg_dump -Fc` + 保留最近 N 份（custom 格式才支持只恢复单表） |
| `.github/workflows/release.yml` | 打 tag → mvn（含单测）→ 构建推送镜像（**不打 latest**）→ 容器级冒烟 → 可选 SSH 部署 |

### 五条设计判据（都对应一类真实事故）

1. **远端不编译。** 远端 build 出来的 jar 与 CI 里跑过 434 条回归的不是同一个文件
   ⇒ 「验收过的产物」和「线上跑的产物」必须是同一个。
2. **镜像 tag 必须具体，禁止 `:latest`。** latest 让「线上是哪一版」无法回答，
   也让回滚退化成「回滚到你正在修的坏版本」。
3. **中间件一律不发布端口。** 公网可达的 PG/Redis 不是配置风格问题，是事故。
4. **`mem_limit` 必须有。** 没有限额，`-XX:MaxRAMPercentage` 只能按宿主内存算，
   「容器感知」是摆设（D42 那条判据在远端才真正生效）。
5. **`up -d` 的退出码证明不了应用能用。** 所以 deploy.sh 必须等容器 health，
   失败就自动退回上一个版本。

### 护栏：`day47-prod-compose-guard.py`（19 条，进 CI）

上面这几条**没有一条**会在编译、测试或 `docker compose up -d` 时报错 ——
只会在上线后的某一天变成事故。⇒ 只能靠静态判据提前拦。

控制组（`_d47_prod_ctrl.py`）4 组全命中、零误伤：
① 给 postgres 加 `ports: 5432:5432` ⇒ 红 1 条；② tag 改 latest ⇒ 红 2 条；
③ 删 `mem_limit` ⇒ 红 1 条；④ deploy.sh 加 `down -v` ⇒ 红 1 条。

### 又踩到一次「落盘静默失败」

控制组第一版跑出「② 没红」，查下来是**写入没有生效**（`open().write()` 返回成功、
随后 grep 到的仍是旧内容）。因为改动没还原，后面几组的失败数是**累积**的 ——
表现极具误导性（看着像「护栏在某些变异下不灵敏」）。
⇒ 修法：控制组的 `write()` 写完**立刻读回校验**，不符就报错；
并且「脏工作区」判定只算已跟踪文件的改动。

> ★ 与 CI 那次同源：**任何「改文件 → 跑校验」的自动化，都要复验改动真的落盘了。**
