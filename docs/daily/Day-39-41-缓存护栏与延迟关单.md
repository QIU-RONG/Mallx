## 三、D41 · RabbitMQ 延迟关单（DLX + per-message TTL）

拓扑（**不依赖延迟插件**——官方镜像开箱即用）：
```
下单(afterCommit) ─▶ exchange mallx.order.delay ─rk=ttl─▶ queue mallx.order.ttl（无消费者）
                                                              │ per-message TTL 到期
listener cancelOne ◀─ queue mallx.order.close ◀──rk=close───┘ (dead-letter)
```
- **afterCommit 发布**：事务内发 → 回滚后消费者去关不存在的单；afterCommit 保证
  「消息 ↔ 已落库的单」一一对应。
- **发布失败只 warn 不抛**：MQ 是加速不是正确性前提——@Scheduled 扫描保留为兜底（双保险），
  两条路径收敛到同一个 CAS（`cancelOne`），重复执行 0 行无害。
- `ORDER_CLOSE_DELAY_MS` 可配（默认 120000 与扫描兜底的 2 分钟对齐）。
- 验收 `day41-rabbitmq-close-verify.py`（12/12）：**订单 6.1 秒被关**——
  扫描是 60s 周期 + 2min 超时，秒级关闭只有 MQ 路径能解释。
- 高水位清理：验收单的 inventory_logs（ORDER_LOCK/CANCEL_RELEASE）与订单本体必须
  psql 物理清——**CANCELLED 单会把 day26 的 6 单基线顶成 7，收集器 (c) 必挂**；
  ledger 残留会把 day14 的「ledger 全空」基线打挂（第一天就撞了，教训：**高水位
  基线类脚本的产物清理要写进脚本本身，不能靠事后手清**）。
