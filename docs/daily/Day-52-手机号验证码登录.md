# Day 52 · 手机号验证码登录 / 注册

> 需求原话：「能不能做登录注册功能，使用手机号验证码登录，如果未注册就要求用户先注册，跳转到注册界面」
> 跨度：后端（mall-user + mall-common）+ 前端（mall-app）+ 验收脚本 + 控制组 + CI。

---

## 一、三个必须自己拍板的决定

### ① 验证码不真发短信 —— 但「不发」这件事必须只有一个出口

真实短信要接服务商（阿里云 / 腾讯云短信），需要账号、签名报备与费用。本机与 CI 都没有。

做法：**存储 / 限流 / 校验逻辑与线上完全一致**，只有「发送」这一步是替身 ——
打一条 WARN 日志，并且**仅非 prod** 把明文码放进响应体（前端自动填入）。

```java
// SmsCodeServiceImpl
log.warn("【开发模式·未接短信服务商】手机号 {} 的验证码 = {}（{} 分钟内有效）", ...);
return isProd() ? null : code;          // ★ prod 恒为 null
```

★ 上线的唯一改动点就是这一处：把 WARN 换成短信 SDK 调用。`acceptsProfiles("prod")` 已经保证
生产**绝不**返回明文 —— **一个会把验证码写在响应里的登录接口，等于没有验证码**。

⇒ 配套保证：`SmsSendVO.devCode` 的注释里写明「接入真实短信后此字段应整体删除」，
前端也是「有 devCode 才提示」，所以生产环境界面上不会出现任何异常。

### ② 未注册 → 专属业务码 `4041`，**不是**普通 400

前端要做的事是「跳注册页」，它必须能**区分**「未注册」和「验证码错 / 过期 / 被限流」——
这四种情况都会走到 `catch` 里。

如果都返回 400，前端只剩两条路：匹配 message 文案（后端改一个字就静默失效），
或者一律跳注册页（验证码打错也被送去注册，荒谬）。

```java
// ResultCode
PHONE_NOT_REGISTERED(4041, "该手机号未注册，请先注册"),
```

前端按码分支（**不是**按文案）：

```ts
if (e instanceof BizError && e.code === 4041) {
  router.push({ path: '/register', query: { phone: phone.value, redirect } })
}
```

⚠️ 为此把 `http.ts` 的拦截器从 `reject(new Error(msg))` 改成 `reject(new BizError(code, msg))` ——
普通 `Error` 里没有数字 code，前端拿不到判据（`BizError` 继承 `Error`，既有 `e.message` 写法全部照旧）。

### ③ 登录校验用 `verify`，注册才用 `verifyAndConsume`

这是本功能最容易犯的错，所以单独说：

```
用户旅程：输手机号 + 验证码 → 点登录 → 系统说「你没注册」→ 跳注册页 → 填昵称 → 提交
```

**注册时用的是同一个验证码**。如果登录那一步就把码消费掉（`verifyAndConsume`），
用户到注册页会看到「验证码已过期」—— 又得等 60 秒重发，**而日志里毫无异常**。

⇒ 拆成两个方法，意图写在接口上：

| 方法 | 语义 | 用在哪 |
|---|---|---|
| `verify(phone, code)` | 只校验，**不消费** | `sms/login`（下游还要用这个码） |
| `verifyAndConsume(phone, code)` | 校验 + 立即作废 | `sms/register`（码换出一个账号，用完即焚） |
| `consume(phone)` | 单独作废 | `sms/login` 走到「已注册」分支后 |

⇒ 生产上的等价物是 **「一次性凭据」与「多步流程」冲突**这个通用问题：
凭据的作废时机必须落在**流程终点**，不是第一个验证点。

## 二、两个安全细节（都不报错，所以必须写下来）

### ① 发码接口**不回答**「这个号注册了没有」

若在发码阶段就回答，任何人拿一份手机号名单刷一遍就能**枚举出平台全部用户**。
所以判断放到「验证码校验通过之后」—— 让「你得先证明你持有这个号」成为枚举的门槛。

### ② 手机号不进日志明文

```java
private static String maskPhone(String phone) {   // 138****0001
```

日志是最容易被忽略的数据泄露面：它会被采集、长期留存、给一堆没有业务权限的人看。

### ③ 占位密码：从设计上关掉密码登录

`users.password` 是 NOT NULL，但手机号登录根本不看它。写一个**连我们自己都不知道**的随机值再哈希，
比设个默认密码（`123456`）安全得多 —— 默认密码是最经典的被撞库入口。

## 三、前端

**登录页做成两种方式并列**（手机号是默认那个），旧的用户名密码**保留**：

1. 它是种子用户（demo / demo123）唯一的进门方式，删掉等于删掉演示路径；
2. `day43 / 46 / 47` 那批端到端脚本全部靠 `/auth/login` 拿 C 端 token ——
   删掉它们会集体变红，而它们验的是订单 / 售后 / 前端契约，**跟登录方式无关**。

**新增注册页**（`/register`）：

- ★ **不加 `requiresAuth`** —— 走到这里的用户还没有身份，加守卫会把他弹回登录页，与「未注册 → 去注册」形成**死循环**。
- 手机号从 query 带入但**允许修改**（用户可能输错号，或想换个号注册；只读会逼他退回登录页重来）。
- 顶部写明「该手机号还未注册，验证后即可完成注册」—— 用户是被转过来的，直接甩表单会让人以为走错流程。
- 注册成功**直接登录**（后端已返回 token）：他刚证明了自己持有这个号，再让他回登录页重输一遍是纯粹的浪费。

**倒计时定时器必须在 `onUnmounted` 清掉** —— SPA 里路由跳走后组件销毁，但 `setInterval` 不会自己停，
它会继续持有旧的 ref，用户还能在别的页面看到倒计时走完（泄漏 + 灵异现象）。

## 四、控制组（4 组，`backend/loadtest/_d52_sms_ctrl.py`）

每组都要经历「改坏实现 → 重建 → 重启 → 回跑验收」，回跑**必须红**：

| # | 变异 | 必须红 |
|---|---|---|
| ① | 去掉发码限流 | `A5` |
| ② | 未注册返回普通 400（丢掉 4041） | `B3` |
| ③ | 登录时把码消费掉（`verify` → `verifyAndConsume`） | `B4`（+ 下游级联） |
| ④ | 占位密码改成 `encode(手机号)` | `C9b` |

### ★ 第 ④ 组当场抓出一条**假绿断言**

原判据是「**哈希串里不含手机号**」：

```python
chk("C9b 占位密码不含手机号", PHONE not in pwd)
```

它是**恒真**的 —— `pwd` 是 bcrypt 输出（`{bcrypt}$2a$10$…`），**里面永远不可能出现明文手机号**。
所以这条断言自始至终什么也没守住。变异 ④ 回跑后 **0 条红**，才把它暴露出来。

⇒ 已换成唯一有意义的判据：**拿手机号当密码去登录，必须失败**。

```python
st, r = http("POST", "/api/auth/login", {"username": PHONE, "password": PHONE})
chk("C9b ★ 该账号不能用手机号当密码登录", r.get("code") != 200)
```

**一般化**：断言必须落在「**可观测的行为差异**」上，不能落在「我没见过某种形状」上。
后者在多数实现下恒真，是典型的**零成本假绿**。

## 五、验收清单（29 条，`day52-sms-auth-verify.py`）

| 段 | 内容 |
|---|---|
| A | 发码成功 · devCode 格式 · **Redis 里真的有这个码** · TTL ∈ (0,300] · 60 秒限流 · 手机号格式 |
| B | 错码被拒 · **错码后码仍在**（失败不消费）· **未注册 → 4041** · **未注册时码未被消费** |
| C | 注册成功 · 直接返回 token · token 真能用（打 `/users/me`）· id 一致 · 库里真有这行 · username == phone · 昵称正确 · **密码是 `{bcrypt}` 哈希** · **不能用手机号当密码登录** · **码已作废** |
| D | 已消费的码不能再用 · 已注册号发码 · **登录成功（不再 4041）** · token 指向同一用户 · 登录后码作废 |
| E | **对照组**：匿名打 `/users/me` → 401（白名单只放行 auth）· C 端 token 打管理端 → 403（跨域隔离未破坏）· 幂等清理 |

★ 「不信接口自报」：每个关键结论都去 **Redis / 数据库**核对一遍
（接口说发码成功 → 去 Redis 查 key 在不在、TTL 对不对；说注册成功 → 去 users 表查这一行写成什么样）。

## 六、两个踩到的坑

### ① 断言照【注释】写，而不是照【实现】写

首跑 28 条只有 `C9` 红：`prefix={bcrypt`。

查下来 `PasswordEncoder` bean 是 `PasswordEncoderFactories.createDelegatingPasswordEncoder()`，
`encode()` 产出 **`{bcrypt}$2a$…`（带 `{id}` 算法前缀）**，而我的断言写死 `startswith("$2")`。

根因是 `AdminCreateDTO` 的一行注释写着「落库结果是 `$2a$…`」—— **注释漂移了**，
而更早的 `day23-rbac-verify.py` 断言其实是对的（`startswith("{bcrypt}")`）。**同一份事实写了两处，注释那处错了**。

⇒ 已同时修：注释改成 `{bcrypt}$2a$…` 并注明「单点真源见 day23 的 B2」；day52 的判据与 day23 对齐。

### ② 控制组把「环境没起」报成了「断言失败」

控制组首跑直接在**基线**中止：24 条断言一起红，看着像「实现全坏了」。

真相是 **Docker 引擎停了** —— Redis 6380 / RabbitMQ 5672 不可达，而应用照样能起
（`/api/hello` 200）。发码需要 Redis ⇒ A1..A5 全红。

⇒ 给控制组加了**前提护栏**：先 `docker exec … redis-cli PING` + `psql SELECT 1`，
不通过就判 **rc=2（环境问题）**，与断言失败 **rc=1** 分开。

**一般化**：把「环境问题」伪装成「断言失败」会让人去修一个根本没错的东西 ——
Day 49 的护栏首跑（路径漏 `frontend/` ⇒ 全部文件读不到 ⇒ 看着像主题全面漂移）是同一类错误。
