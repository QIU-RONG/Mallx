# MallX 文档导航

> 本目录放「为什么这样做」与「当天怎么验的」，代码里的注释放「这一行为什么这么写」。
> 两者不重复：改代码前先看这里相关的那一天，能少走很多回头路。

## 目录结构

```text
docs/
├── README.md                ← 本文件（导航）
├── backlog.md               ← 待办与想法池
├── perf-report.md           ← 性能相关记录
├── api/                     ← 接口清单 / 请求示例
├── daily/                   ← 每日开发记录（Day-01 ~ Day-85）
└── superpowers/             ← 功能设计稿（改造前的 spec，如 C 端重设计、AI 客服）
```

## 每日记录怎么读

- 文件名：`Day-NN-主题.md`，按天递增，一个功能/一次改造一篇；
- 每篇结构大体是：**做了什么 → 为什么这样做 → 验证（真实命令与数字）→ 没做什么 / 边界**；
- 「验证」一节里的数字（断言条数、测试数）是当时的实测值，**过期的数字不要当现状**；
- 同一天追加的改动会写成「增补」小节，不新开文件。

## 常用入口

| 想知道 | 看哪里 |
|---|---|
| 项目怎么跑起来 | 根目录 `README.md` 的「快速开始」 |
| 某天改了什么、为什么 | `docs/daily/Day-NN-*.md` |
| 接口长什么样 | `docs/api/` + 运行时 Swagger `/swagger-ui.html` |
| 验收脚本 | `backend/loadtest/day*.py`（每个脚本自带报告输出） |
| 未来计划 | `docs/backlog.md` |

## 工程约定（摘要）

- 每个功能都要有「可复跑的验证」：单测或 `backend/loadtest` 脚本，数字写进当天文档；
- SQL 迁移按序号放在 `backend/sql/`，只追加不修改历史文件；
- 权限总数、SQL 文件数等常量有护栏脚本（`day47-perm-count-guard` 等），改一处必须同步全部；
- 前端两个应用共用品牌色阶，改主色要两边一起改（`day49-theme-guard`）。
